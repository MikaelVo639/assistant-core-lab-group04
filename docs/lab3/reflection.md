## The strongest violation: III. Config

The monolith most clearly violates [Factor III: Config](https://12factor.net/config), which separates values that vary between deployments from application code. In `lab03/monolith/assistant_monolith.py`, `API_KEY`, `MODEL`, and `DEBUG` are source constants. The `llm()` function also prints the key and part of the prompt when debugging is enabled. Even though the example key is a teaching placeholder, this pattern would expose a real credential if reused. Changing deployment settings requires editing the script.

The refactor separates configuration into `config.py`, with environment variables and optional local `.env` loading. `.env.example` documents settings without supplying a real key, and `.gitignore` excludes local `.env` files. Validated settings are injected through the CLI's `build_service()` rather than read inside `AssistantService`. Values such as `CREDIT_RATE_VND`, `MAX_CREDITS`, and `LOG_LEVEL` can therefore change without changing the service code. The offline stub needs no API key. Any future real provider must receive credentials through configuration and keep them out of logs. Ignoring `.env` helps prevent new accidental commits; it cannot remove credentials already committed. The original monolith is intentionally kept unchanged as a comparison baseline, so its teaching placeholder and unsafe debug example remain visible there.

## The other readings

- [Factor I: Codebase](https://12factor.net/codebase) concerns one version-controlled codebase serving multiple deployments. A single large script is not itself a violation of this factor. Keeping `src/assistant_core`, tests, and configuration examples in this repository gives collaborators a common versioned implementation; deployment-specific settings remain external.
- [Factor II: Dependencies](https://12factor.net/dependencies) requires explicit dependency declarations together with isolation. The monolith imports only standard-library modules, so its size alone does not establish a missing third-party dependency. The refactor introduces Pydantic and python-dotenv, declares them in `pyproject.toml`, and pins direct development/runtime packages in `requirements.txt`. Installation in a virtual environment supports isolation. These direct pins do not constitute a complete lock of transitive dependencies.
- [Factor XI: Logs](https://12factor.net/logs) treats logs as an event stream whose collection and storage are handled outside the application. The monolith already prints to a stream, but mixes answers with debug messages and sensitive content. The refactor separates CLI answers on stdout from structured JSON logs on stderr. Service events contain intent, latency, session, and degraded status; provider failure uses a generic warning. Keys and full questions are excluded. This supports external collection and avoids application-managed log files. The source specifically recommends stdout for logs; stderr is this CLI's deliberate adaptation to preserve clean answer output.

## Packaging and the resulting design

The [PyPA Packaging Python Projects tutorial](https://packaging.python.org/en/latest/tutorials/packaging-projects/) demonstrates a `src` package, `__init__.py`, separate tests, and `pyproject.toml` build metadata. This repository follows that structure with `src/assistant_core`, package discovery under `src`, and a setuptools build backend. Packaging makes the assistant installable and gives its modules a stable import path. It does not automatically provide configuration safety, dependency isolation, or prove a wheel works; installation and integration still need verification. Together, these changes make deployment settings explicit and orchestration easier to test while preserving the original script for comparison.
